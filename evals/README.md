# evals/ — the labelled set and accepted baselines

Started on Day 07 ([lesson](../docs/day-07/LEARN.md), [notebook](../notebooks/day_07_evaluation_baseline.ipynb)). Every retrieval or answering change from Day 08 on is measured on these questions and compared with the accepted baseline. From Day 12, answers are graded too (an answer baseline and the author's reading of every answer), and the series' recorded failures are regression cases. From Day 13, operational changes (tracing, caching, the model client) are checked to change no answer, and the one that could (a semantic cache) was measured like any other change.

## One labelled query

```json
{"id": "d06-02", "question": "When do pay rises take effect?", "user": "alice", "kind": "question",
 "split": "dev", "origin": "day06-check", "tags": ["permission"], "evidence": ["take effect from 1 April"],
 "facts": [], "answer_chunks": [], "restricted_chunks": ["manager-pay-review-guide#overview"],
 "note": "Day 06: the answer is in a managers-only guide alice may not read"}
```

(shown on several lines here; one line in the file)

| Field | Meaning |
|---|---|
| `id` | stable id: `d03-..` Day 03 probes, `d01-..` Day 01 failures, `d06-..` Day 06's check list, `d04-v..`/`d04-i..` Day 04's value and identifier lookups, `d07-a..`/`d07-u..` new answerable/unanswerable questions |
| `user` | who asks: `alice` (all-employees) or `maria` (all-employees, managers). The ground truth depends on what this person may read |
| `kind` | `question`, or `lookup` (an exact value typed as the query) |
| `split` | `dev`: may be used to tune. `test`: written before any system ran on it; report only, never tune |
| `evidence` | strings that must **all** appear, as whole words, in a chunk for it to answer the question alone (written by hand) |
| `answer_chunks` | **the label**: the chunks this user may read that contain the evidence (derived from the evidence on the snapshot, then frozen). Empty: the documents don't answer it for this user |
| `restricted_chunks` | chunks that contain the evidence but this user may not read |
| `facts` | strings a correct answer contains (for answer checks; given exactly when the query is answerable). Day 12's rubric matches them as case-insensitive substrings: a list that includes the right value passes, and so does a fact inside a longer one ("6 weeks" in "16 weeks"); a correct paraphrase fails |
| `tags`, `origin`, `note` | what the query tests, where it came from, and any labelling decision worth recording (v3's and v4's new questions leave the note empty when there is none; v5's new questions start it with "paraphrase of" or "near neighbour of" and their source's id, and their first tag says which) |

## Rules

1. **Labels come from evidence, not from a retriever's output.** Write the evidence from the documents; let `validate()` in the Day 07 notebook tell you which chunks hold it.
2. **Labels belong to a snapshot.** If anything in `data/sample/` or `access-control.json` changes, `tests/test_evals.py` and the notebook fail and list the stale labels. Review each one; don't edit the manifest to make the failure go away.
3. **Any change to the questions is a new version.** Write a new version file (`questions-v2.jsonl`, then `v3`, ...), keep the earlier ones (old baselines refer to them), and give it its own manifest (`manifest-v2.json`, ...) with the version, file name, hash, counts and, if the documents changed, the snapshot; earlier notebooks keep reading their own. `compare()` refuses to compare runs across versions.
4. **Test questions are spent once.** A test question that influenced a decision becomes a dev question; write new test questions.
5. **A baseline changes only by a reviewed commit.** Notebooks write their runs to `outputs/` (git-ignored) and compare them with the file here. To accept a new baseline, read the listed changes, copy the run file over the accepted one, and commit it with the reason. Rank changes where the baseline recorded a near tie (a gap under 0.001) are reported separately, as CPU rounding.
6. **Commit the rule before scoring the test split.** Write the selection rule (or the value itself) into the repository before any run, exploratory ones included, prints test-split results. If test results were seen first, say so: Days 07 and 08 had to (Day 07 LEARN.md, section 9.2; Day 08 LEARN.md, section 7). From Day 09 this is a file in [`preregistration/`](preregistration/), the first commit on the day's branch: the rules and their dev values, what will be reported whatever it shows, and what each decision needs. The notebook asserts that each rule still gives its committed value.
7. **No personal data.** These questions are synthetic. A real evaluation set built from user questions needs the same access control and retention as the documents, and doesn't belong in a public repository.
8. **The v1 test split is used.** Day 09 used it to make two decisions (both "not adopted"), after Days 07 and 08 had seen its results. Its questions now count as used under rule 4: a decision that needs held-out evidence needs new test questions in a `questions-v2.jsonl`, committed before anything scores them. Day 10 did that, and **v2's test split is used too**: its 41 questions decided Day 10's two decisions. Day 11 wrote `questions-v3` (68 new test questions) and **its test split is used too**: it decided Day 11's decision. Day 12 wrote `questions-v4` (76 new test questions) and **its test split is used too**: it decided Day 12's decision. Day 13 wrote `questions-v5` (51 new test questions) and **its test split is used too**: it decided Day 13's two decisions. The next held-out decision needs `questions-v6`, committed with its pre-registration.
9. **A review belongs to an answer.** The reading in `reviews/` grades one exact answer text (its SHA-256). When an answer changes, its review is stale: read the new answer before trusting the rubric's agreement with the reading. Say when a review was written (before or after the run it describes) and whether the reader saw the rubric's verdict.
10. **A recorded failure becomes a regression case.** Add it to `regressions.jsonl` with the status it has today: `fixed` (must stay fixed), `guard` (must always hold) or `known` (pinned exactly as it fails, so that any change is noticed). Change a case's status only on purpose, and update the lesson it points to.

Checked by [`tests/test_evals.py`](../tests/test_evals.py) (no model, a few seconds; all five versions of the questions, all six retrieval baselines, Day 09's, Day 10's and Day 11's settings against their pre-registrations, every Day 11 context rebuilt from the chunk texts, Day 12's answer baseline and reviews against the labels, themselves and the pre-registered rule, Day 13's new questions against their protocol, its answer baseline and cache lookups against the labels and the committed threshold, and the reading of Day 12's live replies against their texts) and by the Day 07 and Day 08 notebooks' sanity checks. A margin under 0.001 marks a near tie; for RRF, whose scores are made of ranks, it is the smallest score gap in an *input* ranking whose swap would move the labelled chunk.
