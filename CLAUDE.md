# Notes for Claude Code — 15 Days of RAG from Scratch

A public, day-by-day learning series on Retrieval-Augmented Generation. Each day adds a lesson, a runnable notebook, LinkedIn slides and a post. Read `README.md`, `ROADMAP.md` and `VISUAL_STYLE_GUIDE.md` before changing anything substantial. If a local `planning/` folder exists (it is gitignored), also read the project instructions and notes in it.

## Commands

```bash
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt               # Python 3.11+
python -m pytest                                        # executes every notebook in a fresh kernel
                                                        # (first run downloads Day 04's model, 133 MB, into models/)
python -m pytest tests/test_evals.py                    # one file per process uses the least memory
python -m pytest tests/test_regressions.py              # the series' recorded failures (Days 12-13), ~20 s
                                                        # (tests/test_slides.py alone exits with code 5, "no tests
                                                        #  collected", without Pillow; its summary line says "1 skipped")

# Slides (optional; fonts and icons are bundled)
python -m pip install -r requirements-assets.txt
python scripts/slides/day03.py && python scripts/slides/render.py assets/day-03   # same pattern for every day
python -m pytest tests/test_slides.py                    # carousel PDFs match their PNGs (needs Pillow)

# Sample PDFs (standard library only); --check verifies the committed files
python scripts/data/make_sample_pdfs.py --check
```

## Layout per day

`docs/day-XX/LEARN.md` · `notebooks/day_XX_<topic>.ipynb` · `linkedin/day-XX.md` · `assets/day-XX/` (PNG + SVG + PDF) · `scripts/slides/dayXX.py` · a test in `tests/`. Add the day to the README index. Tag each published day: `git tag -a day-XX -m "..."`.

Shared code lives in `src/rag_from_scratch/` (Day 02 `ingest.py`, Day 01 `bm25.py`, Day 03 `chunking.py` and `probes.py`, Day 04 `embeddings.py` with the `Embedder` class, Day 05 `index.py` with `VectorIndex` and `sync()`, and `corpus.py` with `corpus_after()`; Day 06 `answering.py` with `Pipeline`, `ExtractiveReader` and `check_citations()`; Day 07 `evaluation.py` with `load_queries()`, `validate()`, the metrics, `sign_test()` and `compare()`; Day 08 `fusion.py` with `rrf()`, `weighted()` and `rrf_margin()`; Day 09 `reranking.py` with `Reranker`, `rerank()` and `rerank_margin()`; Day 07's `outcome()` joined `evaluation.py` on Day 10; Day 10 `queries.py` with `analyse()`, `expand()` and the reviewed map, and from Day 12 `unknown_names_v2()` and `NamesReader`; Day 11 `contexts.py` with `expand_sections()`, `answer_context()` and `why_refused()`; Day 06's prompt and model client in `chat.py`, from Day 12; Day 12's answer rubric in `rubric.py` with `grade()`, `value()`, `closest_call()` and `compare_answers()`, from Day 13). `tests/test_shared_code.py` may execute only the cells of a notebook that define what moved, with the inputs they read built by already-tested shared code (Day 10's class does this), or only the definitions inside cells (imports, functions, classes, literal constants; `definitions_of=` in `run_notebook_cells()`, used by the Day 11 class; the Day 12 class also takes the few non-literal constants it needs with `assignments()`). Notebooks import it after adding `src/` to `sys.path`; `pytest.ini` sets `pythonpath = src`.

Model files (Day 04's embedding model, Day 09's reranker) are downloaded by the notebook (or `rag_from_scratch.embeddings`) into `models/` (git-ignored) from a pinned commit of the model repository and checked against SHA-256 values written in the notebook. Check a model's licence and its training data's terms before pinning it (Day 09's reranker: Apache-2.0, trained on MS MARCO, whose terms say non-commercial research). Never commit model files, never pin a model to `main`, and never load a pickle-based model file (`*.bin`, `*.pt`) from an unverified source. `HF_ENDPOINT` points the download at a mirror. CI caches `models/` keyed by the pinned revisions (update the key in `.github/workflows/tests.yml` when a model or revision is added).

## Rules

- **Never claim a result you didn't run.** Label untested parts as untested. No invented benchmarks or metrics.
- **Teach in the notebook, reuse from `src/`.** A technique is written out in full in the notebook that teaches it. Copy it into `src/rag_from_scratch/` only when a later day reuses it, keep the copy behaviourally identical, and extend `tests/test_shared_code.py` so the copy is checked against the original notebook. Don't edit a published day's notebook to import from `src/`.
- **Notebooks must run top to bottom in a fresh kernel** from the repo root or `notebooks/`, with relative paths only. Commit them with outputs, but no error outputs and no machine-specific paths (a test checks this).
- **Slides must match the code.** Each `scripts/slides/dayXX.py` checks its numbers and IDs against the executed notebook's outputs. Re-run the notebook before rebuilding slides.
- **Pinned dependencies.** Only add a package when a lesson needs it, pin the version you tested, and note the date and Python versions in `requirements.txt`. Every pin must install on Python 3.11 through 3.14 (for example numpy stays on 2.4.x because 2.5 needs Python 3.12).
- **Secrets:** never commit `.env`, keys, `.venv` or caches. Put placeholders in `.env.example` and always offer a free/local path when a paid API is used.
- **Language models (Day 06 onwards):** the default generator is API-free and runs in CI. A real model is optional, configured only through `RAG_CHAT_*` in `.env`, and called only when the notebook's `LIVE_MODEL` is switched on (or `DAY06_LIVE_MODEL=1`); the tests remove that variable. Never commit a notebook executed with a live model, never print or log a key, and never pin tests to a model's wording. Model names and prices change: state the date they were checked.
- **Sample data** in `data/sample/` is synthetic. Changing it changes results: update the notebook sanity checks, the slides and the labels in `evals/` together (the Day 07 notebook lists which labels to review). Day 01 reads only the `.md` files; Day 02 reads every format plus `data/sample/access-control.json` (permissions live there, never in the documents). The PDFs are generated by `scripts/data/make_sample_pdfs.py` and must stay byte-identical (`*.pdf binary` in `.gitattributes`).
- **Notebook outputs on disk** go to `outputs/day-XX/` (git-ignored). Never write into `data/sample/`; demos that modify data use a temporary copy.
- **Security framing:** permissions are enforced in the retrieval/data layer, never by prompt instructions. A metadata filter on `allowed_groups` is not access control by itself (Day 05): its input must come from verified identity, it must not be skippable, and permissions must be synced. Retrieved documents are untrusted input: escape them inside prompts and keep instructions in their own message (Day 06). Escaping protects the prompt's structure, not the model's judgement. A hybrid retriever applies the permission filter in every retriever before fusion (Day 08): a leak that ranks low is still a leak, and a reranker promotes it (Day 09: rank 4 to rank 1). Rerank only candidates that passed the filter. A query transformation (expansion, rewrite, decomposition) changes what is searched for, never who is searching: identity and filters come from the login, never from the question's text (Day 10). Any step that fetches content by position or id instead of by search (neighbouring sections, a parent document, a linked document, a cached answer) bypasses the search's permission filter: check permissions again on everything it adds (Day 11). A cache key holds everything its result depends on: an answer's key holds the asker's groups (not only the question), the index fingerprint and the pipeline's version, and a cached answer's citations are checked against the asker again before it is served (Day 13: a key without the groups served a managers-only answer to an employee; one without the fingerprint served a policy's old value after it changed). Traces and logs hold ids, scores, decisions, timings and token counts, never document text, the question's text or a key (Day 13 checks every trace); treat them as sensitive anyway (chunk ids name documents).
- **Evaluation (Day 07 onwards):** `evals/` is versioned like code. Labels come from evidence strings, never from a retriever's output, and belong to the snapshot in `evals/manifest.json`; never edit the manifest to silence a stale-label failure. Any change to the questions is a new version file. Never tune on the `test` split. Notebooks write runs to `outputs/` and compare them with `evals/baselines/`; a baseline changes only by a reviewed commit that says why. Report counts and intervals, compare per query, and list every error with a diagnosis. A later day first checks that the earlier retrievers still reproduce their accepted baseline (Day 08 does this for Day 07's), so every difference is its own. Compare a number computed now with one recorded on another machine within its rounding or tolerance (`compare()` allows 0.005 on scores; model scores differ slightly between machines, and Day 10's first macOS CI run differed from Day 09's baseline in a margin's fourth decimal); compare two computations on the same machine, such as a `src/` copy and its notebook, exactly. Fusion weights and other tuned settings are chosen by a rule on dev only, committed before any run (exploratory ones included) prints test-split results; if test results were seen first, say so plainly (Days 07 and 08 had to). From Day 09 the rules, their dev values, what will be reported and each decision's criterion go into `evals/preregistration/day-XX.md` as the branch's first commit, exploration scripts drop test rows at load, and the notebook asserts that each rule reproduces its committed value. Say which reported numbers are in-sample. The v1 test split has been used to decide (Day 09), v2's (Day 10) and v3's (Day 11): a decision that needs held-out evidence needs new test questions in a new version file (`questions-v4`), with its own manifest so earlier notebooks keep reading theirs, committed with the pre-registration before anything scores them. A change that adds context (more chunks, neighbouring sections, a parent document) can't lose against the context it extends and always "finds" more: compare it also with a control that sends the same amount the simple way (Day 11). Every retrieval step that can be switched on needs an off-switch that reproduces the old behaviour exactly (assert it) and a per-query trace. The v4 test split is used too (Day 12), and v5's (Day 13): the next held-out decision needs `questions-v6`.
- **Answer evaluation (Day 12 onwards):** grade answers, not only retrieval: Day 07's `outcome()` against the facts, the step that refused, groundedness, citations, and the stage that lost the answer (Day 12 notebook, section 3). Grounded isn't correct; keep refusals in the grade. Measure the grader against a reading of the answers whenever the generator changes, and keep the reading in `evals/reviews/`, tied to each answer's text. A decision between pipelines needs a value per answer (a cost for wrong answers) stated before the test. A near-tie rule should set a question apart only if flipping its close call can change the outcome (Day 12's rule was broader; say so when it matters). Later days compare answers with `evals/baselines/day-12-answers-v4.json` (`compare_answers()` in the Day 12 notebook).
- **Operations (Day 13 onwards):** an operational change (tracing, caching, timeouts, retries) must not change an answer: compare the answers with and without it for every question (Day 13 asserts it for all of v5), and compare the run with the accepted answer baselines. A cache that serves an answer to a *similar* question is a change to answers, measured like one (Day 13's semantic cache wasn't adopted). Give the model client a timeout per attempt **and** a deadline for the whole step (a timeout per read isn't a deadline), retry only what can pass (connection errors, timeouts, 408, 409, a 429 that isn't a billing code, 5xx), honour `Retry-After` only if it fits the deadline, add jitter, and never retry a key or billing error. A fallback answer is a decision with a cost: Day 13 measured the API-free reader as a fallback and didn't adopt it. Timings belong to a machine: report them as descriptions, never pin them in tests or baselines.
- **Regression tests (Day 12 onwards):** every failure a lesson records becomes a case in `evals/regressions.jsonl`, run by `tests/test_regressions.py` from `src/` only: `fixed` must stay fixed, `guard` must hold, `known` is pinned exactly as it fails. Change a status only on purpose and update the lesson it points to; never delete a known case to make a run pass. A notebook or slide builder that checks the registry counts only the cases recorded up to its own day (Day 12's read R01–R29), so a later day's new cases never break an earlier day.
- **Test memory:** in `tests/test_shared_code.py`, keep one class per day with class-scoped fixtures that release the notebook's namespace (`release()`), so only one day's model is loaded at a time.
- **Visual style:** whiteboard sketch (see `VISUAL_STYLE_GUIDE.md`), built with `scripts/slides/kit.py`. Keep text to short labels; let icons and arrows explain.
